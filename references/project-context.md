# Project background before Work

## Enter when

Bootstrap or next reports project_setup, or project facts/scope/bindings need recovery.

## Execute

Known field-category conflicts are rejected before saving: FastAPI is a
framework, not a build tool. `diagnostics` identifies the expected field; ask
only for the still-missing build choice. Custom technology names remain valid.
Legacy miscategorized records are reported as context conflicts. Correct them
using observed user evidence, then review affected Work bindings; do not claim
the old invalid field authorized a product-stack migration.

Honor provider installation and the required host restart first. Then restore
the original user request, inspect product facts, confirm only missing choices,
save project background, and declare verification before starting a product Work.

Use `cao project inspect` to obtain established product manifest paths and actual
host-observed user evidence IDs. `cao project context set --help` lists structured
fields. Example: `cao project context set --language Java --build-tool Maven
--test-framework 'JUnit 5' --source user-specified --evidence <user-id>`.
The evidence must really cover those fields. A source label, Agent reason,
self-written SPEC or template does not authorize technology. If the host cannot
observe the choice, restore explicit choices through a user message; do not invent
an approval record. For existing product facts, use repository-established and the
observed manifest path, accepting only the fields that manifest establishes.

No Work is needed for project context. Do not create a temporary Work or use Work
decision to store the project stack. Missing fields stay pending; mark individual
irrelevant dimensions with --not-applicable only with actual supporting input.
For explicit modules pass --scope and --path. Root constraints apply to modules.

For an empty product, follow [project initialization](project-initialization.md):
confirm applicable identity/layout, plan/apply exact minimal files, then execute
real project checks before business Work. `verification configure --plan-only`
remains a non-executable declaration; it cannot make any project ready. Existing products reuse actual entries and run `cao verification check` before creating Work, without template overwrite.

New Work: `cao start --requirement <path> --scope <module>` inherits background.
Legacy Work: establish background and use `cao project bind --work <id>`; preserve
its phase and original runs. Changed applicable background needs reviewed
`project bind --refresh`; no old result is recertified. Do not repeat intake.

Use context show/diff and project decisions for provenance and accepted history.
Material replacements use `context change propose` then `change apply --change
<id> --work <owner>`. Only the owner can progress that affected migration scope;
verification review/reanchor and both acceptance parts remain mandatory. done
stabilizes a successfully verified migration. Reverting background does not revert
product code; never reset or overwrite user files to recover.

Final delivery: execute `cao verify`, then real requirement/native acceptance.
`cao acceptance criteria` derives source references from the requirement and
native criteria/Intent. Native declarations can map source IDs with `covers`.
Use `cao acceptance configure --executor-command "<actual check>"` (or --executor-skill) to derive and save the declaration from existing sources without hand-writing another JSON; pass --spec if not already bound. They remain responsible for genuine checks per criterion; matching text or a
mapping is not execution proof. Use existing `sdd acceptance configure/run` or
begin/submit protocol; `cao acceptance` provides the same commands. light still
needs actual behavior evidence even when no formal native checklist exists.
Inspect `cao acceptance status --work <id>`; technical and task evidence must both
pass and remain fresh, and native approvals/reviews/plans must also be complete.

## Exit when

Current scope background and applicable initialization/verification are ready; rerun bootstrap and follow its sole next action.

## If blocked

Follow the structured reason and project inspect/diff output. Preserve the original request and existing Work; never recreate it to repair project context.
