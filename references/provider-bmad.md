# BMAD native execution

## Enter when

The current Work selects `bmad`. Read only this Provider guide and the installed native instructions required for the current action.

## Execute

use installed `bmad-build`; it selects `oneshot` for suitable small work. Follow its exact renderer and reviewers, not an invented `bmad quick-fix`. A recognized oneshot SPEC intentionally has only metadata, Intent and Implementation Notes. Bind with `cao sdd spec bind --spec <native-spec.md>` without criteria selectors: CAO binds native Intent and the current requirement, preserves the file unchanged and does not claim an explicit acceptance checklist. Normal SPECs or explicitly selected criteria keep the existing structural standard checks. Rebind changed bytes and re-verify; no separate workflow/plan/final-acceptance record is required for light.

### Route, approval and implementation

Read the installed `bmad-build` SKILL.md completely and run its exact renderer only when required. Renderer success loads instructions; execute the real workflow and record `invoke skill <name>`, never a renderer plus `-> step-01..05` pseudo-command.

When Build produces its primary SPEC, immediately run `cao sdd artifact bind --artifact <actual-spec.md>`. Submit `cao sdd route propose --declaration <route.json>` before implementation. Use the route declaration contract linked directly from SKILL.md for fields and real rule hashes/quotes, required artifacts and every omitted document's reason/replacement. Direct Build can retain standard gates.

Resolve all native Open Questions. For dispatch, present the full SPEC summary/path, run `cao sdd approval request`, and wait for a host-observed standalone `批准并继续` / `批准并停止` (Approve and continue / Approve and stop). Generic continue, technical choices, Agent statements and status edits do not approve. Approve-and-stop pauses implementation until explicit continuation. Approval binds Work, host session and question/tool-call ID; new sessions must receive current context first.

Follow the actual step-03 implementation handoff; set SPEC in-progress and baseline_commit first. Use the native implementation child session where required and available; use the installed fallback when unavailable. Full planning requires native Finalize, memlog/audits and required PRD/architecture reviews, not draft artifacts.

### Native review and close obligations

These obligations follow the actual BMAD oneshot route for light, standard and comprehensive profiles. A route-bound primary SPEC is sufficient to identify them; standard/comprehensive must not bypass them by omitting a light `spec_binding`.

Before business implementation, configure verification and explicitly reanchor an existing Work if needed. The host blocks business writes until that baseline is accepted; native CAO/SDD artifacts, manifests and initial test/verification scaffolding remain writable. Tests do not have to pass before implementation. Do not install dependencies or expand scaffolding into implementation without the applicable authorization.

For BMAD oneshot, execute every active Review layer and Classify step in the actual rendered `step-oneshot.md`. Record each ticket with `cao sdd review begin --layer <active-layer> --instructions <rendered-step-oneshot.md> --model <current-model>`, launch independent reviewers as the native prompt directs, preserve their raw Markdown and submit triage evidence with `cao sdd review submit --layer <active-layer> --report <provider-owned-report.json>`. Use the native external-session handoff when subagents are unavailable; never replace it with primary self-review or invented reports. Begin returns the evidence fields. All layers must be current before CAO verify; changed code/intent/instructions/reports require review again. Finalize the native SPEC, review/rebind changed bytes, and verify. Follow the native Commit step when Git is available; uncommitted Work product/SPEC changes block done. Never push unless authorized.



For dispatch, begin EVERY active step-04 layer with the actual rendered `step-04-review.md`, collect raw JSON findings with unique IDs, then `cao sdd review classify --layer <layer> --report <provider-report.json>` for every layer BEFORE product patches. Classify each raw ID exactly once, including empty arrays for zero findings; then apply patches and native checks and `cao sdd review resolve --layer <layer> --report <provider-report.json>`. Preserve original reports and independent identity. Frozen-intent violations require native intent_gap/bad_spec loopback; defer only evidence-backed outside-intent work. The route contract contains the exact report shapes and audited execution recovery.

Bind ALL current requirement stories/epics using repeated `cao sdd plan bind --plan-item <sprint-status.yaml-or-yml>#<story-id-or-epic-N>`. A project sprint may include unrelated historical work; do not bind or complete it merely because the file exists. Without a separate plan, Direct Build still must finish its SPEC Tasks & Acceptance; `--no-plan` cannot waive these tasks. oneshot may legitimately have no task plan. Use actual native status/task progress as lifecycle source, regardless of title/filename spelling; native done means review, not CAO completion.

## Exit when

Current requirement tasks and applicable pre-verification obligations are complete; follow completion guidance and the native order for any remaining Commit/close steps. Standard/comprehensive retain workflow registration and independent final acceptance; light still honors native prerequisites.

## If blocked

Inspect `native_sync` diagnostics and associate the actual source. Source sync does not refresh acceptance hashes: review changed SPEC/criteria, explicitly rebind if needed, and reverify. Never invent entrypoints, reports or historical execution.
