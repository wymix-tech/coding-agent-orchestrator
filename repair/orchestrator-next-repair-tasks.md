## T1：状态与历史的事务边界

依据：`_commit` 与 `_dump` 在当前包中仍与原包相同。版本检查、状态覆盖、历史追加未处于可恢复事务中；临时文件名称固定。

验收：

1. 两个独立进程从同一 revision 提交不同更新。可以一方成功另一方得到明确版本冲突，或在规定的重载重试后依次成功；不能同时成功却丢失更新，不能出现两条相同的 revision 边。
2. 进程间锁覆盖实际提交边界；锁超时、持有者异常退出具有确定行为。线程内锁或唯一临时文件不能代替事务设计。
3. 注入状态写入、历史写入和提交各阶段的崩溃，恢复后处于完整旧状态或完整新状态，状态与历史一致。单纯 os.replace 两个文件不足以证明这一点。
4. 每次提交具有稳定身份，恢复与重试不会重复记账。保留外部 YAML/JSONL 接口或提供明确迁移。
5. 不在提交锁内运行 CBM、项目测试等长耗时操作；提交时重新校验所用状态和证据版本。声明支持的平台，未运行的平台不能报通过。

## T2：工作项身份与需求修订

依据：当前 `_ensure_state` 仍在状态存在时直接复用；全局 intake 目录仍会覆盖分析输入。

验收：

1. WORK-A 活动时 intake 显式 WORK-B，必须返回冲突/明确切换操作，不能沿用 A 的身份处理 B，也不能先覆盖 A 的需求或产物后再拒绝。
2. “重新分析当前工作项”“修改当前需求修订”“创建/切换新工作项”有明确、可审计的语义；不能只比较标题或默认 request hash。
3. 相同需求同一修订重跑保持身份和产物引用一致；语义范围或验收标准变更后，相关 acceptance_satisfied、任务完成和验证证据不能静默继承。
4. 分析产物按工作项/修订隔离，在暂存区完成后统一提交引用；模拟管线中途失败、两个 intake 交错运行，仍能恢复上一个完整一致版本。诊断产物可以保留，但不能被当作当前可执行分析。
5. A 完成后添加 B 的需求文件，不应因全仓快照变化而把 A 的历史完成事实自动撤销，更不能复用 A 处理 B。区分冻结的历史完成记录与当前代码的关闭准备；当前权限仍检查实时证据。
6. 新的状态/产物目录纳入共享材料分类；生成文件不能再次污染代码快照。若旧数据无法可靠识别身份，输出迁移问题，不猜测合并。

## T3：Policy 快照的语义与来源

依据：`policy_engine.route` 仍只将 stage、context、规则 ID 列表和 manifest 路径用于快照。新增输入哈希已缓解错误放行，但不能证明这个 Policy ID 本身正确。

验收：

1. 同一 rule ID 下修改规则正文、约束、级别、适用范围、required、执行命令或 override 合并结果，policy_snapshot_id 必须变化。
2. 相同有效策略具有确定快照；绝对目录位置不是策略内容身份。不能随意排序有语义顺序的字段。
3. 追踪 manifest 实际引用的 policy pack、override 与其他有效来源，包括标准 policies 目录之外的文件；缺失、删除、不可读应明确失效。
4. Context Manifest、分析内容绑定、验证计划和门禁引用同一份生效策略结果，不出现各自不同的策略版本。
5. ECC 等外部指导不能因被追踪就自动升级为项目 MUST；保留项目规则优先级及显式提升机制。

## T4：持久化显式 SDD 选择

依据：project_bootstrap.py 未改；已有配置时无 force 就保留整份旧 config。

验收：

1. 同时存在 OpenSpec/BMAD → 首次 init 有歧义 → 执行 init --sdd openspec → 后续 start 不再因同一选择阻塞。
2. 对明确选择做字段级合并，只清除相应 unresolved。保留项目定制的 Policy、host、其他配置和无关阻塞，不要求 --force。
3. init 输出、落盘 config、Bootstrap Guard 对最终状态一致；重复运行幂等。
4. 已有活动任务的原生归属与新选择冲突时给出明确处理结果，不能只改配置而留下矛盾状态。

## T5：历史需求去重

依据：当前 start_router 仍只比较最后一个完成 work ID 与候选正文默认 hash，没有完整历史映射。

验收：

1. A 完成并归档，B 完成，再 start：不自动重开 A。
2. 自定义 work ID、native story ID、重新启动进程后仍能正确去重。
3. 稳定 requirement ID 与 revision 分离：正文 hash 可标识修订，不能单独充当身份；相同正文但不同身份不能误合并。
4. 同一身份的新修订进入显式修订/选择流程，不能被永久当成旧需求，也不能静默复用旧验收。
5. 无历史映射的旧包保持可读，采用保守迁移；依据不足时不自动重启、合并或宣称已完成。

## T6：BMAD 发现

依据：当前 requirement_discovery.py 未改，主要扫描安装目录，不使用 detector 已识别的 native 状态位置。

验收：

1. 能处理 `_bmad-output/implementation-artifacts/sprint-status.yaml` 与 story 同目录的项目夹具，以及显式配置的输出位置。
2. 发现逻辑与 detector 共享有效项目/native 状态来源，按真实工作项 ID 和状态定位需求。
3. 排除安装模板、示例和工具资源；正文有 story/task 字样不能成为唯一高置信度依据。
4. 完成/归档工作不被当作待启动候选；多候选或未知 native 格式时返回有来源的待选择/定位信息。
5. 声明实际支持和测试的格式；该缺陷依据是包内扫描器不一致，不代表所有 BMAD 版本都已调查。

## T7：验证义务与结果的生命周期

依据：独立离线流程中，合成 CBM 数据先误报跨项目边界，修正后计划已移除集成项，但已确立的必要门禁仍 pending。拒绝关闭是正确的；目前缺少正常的、有依据的义务变更路径。这属于设计补齐，不是放松门禁。

验收：

1. 定义稳定 obligation ID、来源、适用工作项/修订与状态；执行结果只记录其所覆盖义务和证据。
2. 计划变化不能无痕删除既有义务；确属不再适用时，通过项目规则认可的、有原因/依据/来源和审计记录的变更处理。
3. 区分“通过”“被后续义务替代”“经授权不适用/豁免”，不能把后二者伪装成测试 passed。
4. 单纯改 required=false、漏掉计划条目或耗尽重试次数仍不能关闭；无法证明变更有效时继续拒绝。
5. 新任务的义务不继承旧任务的错误范围；生效义务仍全部通过共享 action_guard 检查。

## T8：完整闭环与外部集成

1. 实跑：空仓库 → 初始化 → 写需求 → intake → 解决证据缺口 → 实现 → 代码修改/重分析 → 评审 → 必要门禁 → 最终验证 → 关闭 → 新需求 → start 正确定位。
2. 同时验证成功关闭与证据不足拒绝；禁止用假 passed 结果、错配项目名的 fixture 或删除必要门禁拼出成功路径。
3. 比较同一输入下 check、pre_tool、transition、verify、Stop、start/resume 的共享动作判定；区分完成角色和全局关闭。
4. 对真实宿主采集的事件与工具参数建契约 fixture，验证原始 patch、cmd/command、失败工具调用、角色交接和恢复。没有真实宿主时只报告离线测试通过。
5. 当前 CBM adapter 仍在任意非零退出后尝试 `cli --raw`，且可能只报告后一次错误。先核对目标版本 help/能力和官方文档；区分“不支持调用格式”和“业务调用失败”，后者不能靠重复换语法吞掉原始错误。测试非零退出、超时、stdout/stderr、JSON 解析、索引和变化检测。
6. 兼容性结论必须注明具体 CBM、宿主、OS 版本与证据；缺少环境时交付复现命令和明确的未验证项。不能把离线 fixture 标成真实 CBM 验证。
7. 更新中英文说明、Schema、变更记录及实际测试数量；继续通过 Skill 上下文预算检查。最终交付完整源码 ZIP、修复说明、测试报告、SHA-256 和迁移说明。
