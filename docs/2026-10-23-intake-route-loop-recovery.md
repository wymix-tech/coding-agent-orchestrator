# Intake 与 native route 循环修复

## 问题与目标

2026-10-23 的 Pi 会话由用户主动终止。模型持续提交 `omitted[0].replaced_by: null`，CAO 返回错误码和整段启动提示，未给出字段修复条件。此前的空需求模板准入、FastAPI 被记录为构建工具、安全风险漏报，使后续判断失去可靠输入。

本轮基于已合并 PR #18 的 main 实施，保留 Work、原生规则证据、审批及验收边界。

## 实施顺序

1. 路由声明的身份、字段、产物和遗漏职责错误都提供结构化诊断；返回输入修复标识，明确输入未变时不得重试。light 已接受项目背景后不再重复启动说明。
2. 区分原生 oneshot 中确实不适用的职责与由产物替代的职责。不适用声明必须绑定包含 oneshot 路由规则的现有证据；dispatch/full-planning 不得借此豁免。
3. 拦截未填写的 CAO 需求模板，不要求任意格式的用户需求改用模板；已有任务发现该问题时给出原地恢复路径。
4. 对已知工具的字段类别冲突提供诊断，保留未知自定义技术名；不把缺失的构建工具自动补成模型偏好。
5. 对需求正文中明确的认证、密码、令牌等风险补充最低风险标记；旧评估漏报时要求重新评估，不静默清空已有进度。
6. 精确允许 Python JSON 只读格式化，继续拒绝写出文件及任意解释器代码。
7. 将依赖安装准备限定到项目虚拟环境或项目包管理范围，拒绝全局安装及 `--break-system-packages` 等越界选项。

## 验证

重放空模板、错误技术字段、遗漏职责 null、规则证据错误、oneshot 不适用声明、遗留风险评估、只读 JSON 管道和全局 pip 安装序列。确认失败不改写需求/Work/路由历史，修复后可继续，未解决原生问题仍阻止实现。执行相关回归、全量 Python 和 Pi 合约测试。

## 实施结果

上述七项已完成。新增 12 项回归测试；原有生命周期/计划/门禁测试中借用认证描述作为通用夹具的部分，改用明确的非安全场景，避免继续把认证需求预期为 light。空模板夹具改为先填写真实正文。

- Python 全量 892 项通过，按模块分四组执行。
- Pi 适配器 36 项通过，类型检查通过。
- wheel 构建、干净虚拟环境安装及仓库外 CLI smoke 通过，覆盖内置 Provider 和模拟宿主。
- `git diff --check` 通过。

`repair_id` 是稳定的恢复协议标识，不会强制终止模型或自动跳过门禁。风险补充只识别需求正文中的明确敏感行为，字段类别校验只针对已知技术名；它们不替代 Agent 对完整需求和原生规则的判断。本轮未再次调用原会话模型执行完整开发会话，仍需真实会话复测纠错效果。
