# 全 profile 双验收与 light 最小原生流程设计

## 1. 需求与审批状态

用户已确认以下原则：

- 所有 profile（light、standard、comprehensive）都必须通过技术验收与独立 SDD 收尾验收。
- 即使 SDD 之前已经确认功能验收，CAO 仍须组织针对当前实现的新一次需求/设计验收。
- 使用混合执行：可运行命令由 CAO 实际执行；只有原生 Skill 时由 Agent 重新执行并提交逐项证据。
- light 的前置最低限度为 Provider 最简原生流程产出的 SPEC 和明确验收标准。

用户已确认本文书面设计；进入实施计划与当前会话顺序 TDD。新门禁尚未实现，
不将设计审批或计划提交当作功能验证通过。
继续当前隔离 worktree、顺序 TDD，不使用子代理，不自动推送、合并或发布。

## 2. 当前实现与缺口

现有 `cmd_sdd_workflow` 持久化 select/execute/complete、原生产物及计划范围。
`completion_status` 检查原生 workflow 证据、关联计划、执行门禁和新鲜的配置绑定验证。
`cmd_done` 可以调用项目配置的 `sdd.command.transition done`，随后重读完成条件。
这些机制不等于强制执行一次独立、逐项覆盖当前需求/设计标准的收尾验收。

当前 light 的基础门禁仅 targeted_verification；新增规则必须在所有 profile 的完成计算中
显式检查，不能只依赖 standard 的人工评审门禁、任务勾选或流程名称。
已有首次项目引导、提醒模式、事务、验收绑定、路径所有权与原生流程记录保持独立职责。

## 3. 完成契约

完成条件是以下各项的交集：

1. 当前需求与评估有效，原生流程已实际执行，必要工件与关联计划满足原有契约。
2. 技术验收通过且新鲜：实际运行项目配置的 required 脚本，满足项目明确的单元测试、
   覆盖率及其他适用规则。测试能力继续显式声明；不能以 light 为由少跑 required 检查。
3. 独立 SDD 收尾验收通过且新鲜：所有绑定的需求验收项、设计约束均有本次通过结果及证据。
4. 其他当前 profile 的必要评审门禁满足；无未解决 blocker。

技术标准由项目明确配置，不新增统一覆盖率百分比，不猜测测试框架，也不以空测试假成功。
light 的 SPEC 必要约束可承担轻量设计来源，不要求额外独立设计文档。

`cao done` 只复查和关闭，不在一次调用中暗中启动长时 Skill/LLM 评审。
未通过时返回未满足的具体门禁及下一步验收动作，Work 保持 active。

SDD 收尾验收是自动派生的硬门禁，不能用 `gate satisfy` 手动填通过，也不能由
`--allow-unverified`、旧 workflow completed、旧验收报告、全勾选计划或 CLI override 替代。
旧入口/失败例外仅保留原有审计意义，不豁免新的收尾验收。所有 profile 均适用。

## 4. light 的最低前置契约

light 降低的是规划深度，不是完成可信度。CAO 仅要求：

- Agent 实际执行已安装 Provider 支持的最简原生规格流程，不能用 echo/mkdir 等占位替代。
- 落地一个真实的原生 SPEC，说明目标、范围、必要约束，以及可逐项验收的标准。
- 验收标准可以是 SPEC 中的章节，不必另建标准文件；仍需非空、明确、可观察。
- 使用 Provider 自己的文件名与目录，不强制叫 SPEC.md，也不复制到 CAO 目录制造第二份规格。

CAO 不为 light 强制额外 PRD、架构文档、Epic、Story 或 tasks 计划。
没有计划可以使用原有显式 no-plan 声明；已存在/已绑定的相关计划不能被静默删除或忽略。
单纯落地 SPEC 和标准足以满足这个最低前置要求，但不代表实现或收尾验收已经通过。

Provider 原生必要前置仍需遵守：优先选择合法的最轻入口。若已安装版本没有这样的入口，
告知用户限制并请求流程调整，不伪造原生执行，也不擅自生成整套重型工件。
standard/comprehensive 保留其风险所需的原生规划深度，同样必须有验收来源和收尾双验收。

## 5. 验收范围与标准绑定

Agent 根据当前原生 SPEC/设计/验收清单建立 Work 级的轻量绑定：

- Provider、原生 SPEC 引用、验收标准来源、必要设计约束来源。
- 本次需求必须覆盖的唯一条目 ID 及来源引用；同一个文档可同时承载 SPEC、标准和约束。
- 验收执行模式与真实命令/原生 Skill 入口；不得只登记一个名称或说明文字。

不要求 Provider 改成通用工件格式，不由核心猜测自然语言标准，也不建立评分卡、事实模型
或证据图。Agent 必须忠实绑定全部适用条目，不能为了完成任意缩减清单；不确定时先问用户。
核心检查来源存在、路径归属、条目唯一且非空、声明完整及后续逐项覆盖，不宣称可以机械
证明任意自然语言清单已经完整提取。

范围与执行声明属于验收标准的一部分。SPEC、标准、设计来源字节或绑定条目变化时，
相关证据失效；需要显式审阅/重锚，而非自动认证新标准或删除不通过的条目。
来源不能使用无关 Work 的工件；沿用真实路径与 Provider 所有权检查。

## 6. 混合执行与本次结果

### 6.1 命令模式

CAO 在技术验收通过后，创建本次 run，冻结输入并调用项目声明的真实验收命令。
命令需要针对绑定的需求/设计标准独立验收当前实现，产生逐项结果，而不仅返回 exit=0。
零条目、缺项、不可解析结果、缺工具/依赖、超时或非零退出不能认定通过。
核心不内置框架模板、不解析 Maven/npm 等第三方报告、不调用 LLM；具体语义由受信任
项目包装器承担。不能把一次普通技术 verify 的结果自动转换成 SDD 验收结果。

### 6.2 原生 Skill 模式

CAO 创建本次 run 并返回冻结的需求/设计/条目范围和已安装 Provider 的真实验收入口。
Agent 必须读取并执行该原生 Skill，对当前实现逐项重新验收，再通过 CAO 专用接口提交结果。
入口不可用、无法执行、无法判断或缺少证据时保持 pending/blocked，不替换成一般口头评审。

必须有当前 run 标识、逐项结果、可复核证据引用及必要理由。单句“SDD 已确认”“全部通过”，
旧 run 的报告或仅一次手动 gate satisfy 均不接受。Agent 执行中仍可记录 checkpoint、决策与 blocker。
核心可核实范围覆盖、run 绑定、证据文件与新鲜度，但不能仅靠 JSON 或 run ID 证明任意
Skill 真正执行过或语义正确；该信任边界须在指导、测试和验证报告中明确披露。

### 6.3 结果约束

两种模式使用同一最小 CAO 结果接口，原生文档仍归 Provider：

- run ID 与绑定输入身份；执行入口/模式及实际执行结果。
- 每个预期 ID 恰好一个结果：passed、failed 或 blocked，并有可复核证据/理由。
- 原生报告和证据的引用与字节 hash；CAO 自己的结果回执由 CLI 持久化。

只有完整覆盖且每项 passed 才可派生通过。缺项、重复、未知 ID、空结果、缺证据、
failed/blocked 或整体执行失败都阻止完成；不能靠 overall passed 覆盖逐项失败。
新一次执行先清除旧通过资格；中断、提交失败或执行失败不得保留上一轮成功作为当前成功。

## 7. 新鲜度、顺序与副作用

推荐顺序：

```text
最简/适用原生规格与验收标准 → 实现 → 技术验收通过
                                  ↓
                        独立 SDD 需求/设计收尾验收
                                  ↓
                  必要的技术重验 → 双验收均新鲜 → cao done
```

本次结果绑定需求、Provider、评估 revision、SPEC/标准/设计来源、实现与规则快照、
技术验收标准和原生验收执行声明。不能靠时间戳或文档中“已通过”判断新鲜。
SDD 验收开始前技术证据必须有效；最终关闭时两种证据都要对应当前输入。
验收发现问题并修复代码后，必须重新进行技术与 SDD 验收，不能在旧 run 上改成 passed。

CAO 派生回执保存在已有被保护的派生状态中，不影响实现快照；不允许 Agent 直接手写状态。
Provider 生成的验收报告仍留在其原生目录，输出与输入必须区分：仅显式登记并校验为本次
验收输出的精确文件路径可作为派生输出单独 hash，不能排除整个 Provider 目录。
输出路径必须在执行前登记、位于当前 Provider 的 Work 级验收输出范围，并与所有输入
和产品文件分离；首次登记只接受尚未存在的验收报告路径，后续复用仅限已有本次 Work 的
验收记录所拥有的输出。真实路径、别名与链接不能把 SPEC/设计输入或既有产品文件伪装成
报告排除。Provider 若只能修改输入文档来写报告，需先适配输入/输出分离，不能静默放宽。
技术与 SDD 快照采用一致的输出边界，并将边界声明纳入验收绑定；未登记文件的变动仍使
证据 stale，必要时重做技术验证。
实现计划需正式测试报告生成不会导致永远 stale，同时任意产品变更不能被这些排除隐藏。

长时执行不持仓库锁。开始/提交时使用既有事务，提交前重读绑定输入；执行期间输入变化
记录 stale 而不是覆盖并发更新。无关的并发决策不丢失，也不因 Work revision 单独变化
无端判为验收标准变化。沿用有界输出、timeout、进程树清理和持久事件机制。

## 8. 状态与兼容

独立结果保存为 Work 的 SDD 收尾验收记录，不覆盖 `sdd.workflow`。
区分 unconfigured/pending、running、passed、failed、blocked、stale；Dashboard 显示两种
验收及下一步，不能把原生 completed 或新验收 passed 当作 Work completed。

缺配置/缺标准仍以 Host 提醒指导，产品和 intake 写保持 allow；派生状态写保护不变。
开始/恢复时保留现有 Work 身份、决策、执行状态和语言偏好，不自动重锚或另建 Work。
历史 completed 只保留历史，不自动重开或重新认证。旧 active/reopened Work 在新完成
契约下补齐标准绑定与新验收；旧证据不得凭迁移自动获得新门禁通过资格。

## 9. 实现边界

沿用 JSON、标准库、既有 CLI、锁/原子写入和 Provider 路径规则。
新增聚焦的小模块承载验收声明、结果校验和新鲜度；CLI 负责路由，命令执行复用有界 runner。
扩展完成策略、验收绑定、指导、Dashboard 和正式协议/回归，不全面重写大型 CLI。
新增代码文件小于 500 行；技术栈脚本和验收语义仍由项目/Agent/Provider 负责。

验收声明/创建 run/命令执行/Skill 结果提交通过独立 `sdd acceptance` 命令族表达，
不是给现有 workflow complete 增添一个可以手动勾选的布尔值。具体参数在实施计划确定。
不新增内部主动 turn，不把 Hook 改成产品写硬拦截，不在线安装 SDD/依赖或修改外部登录项目。

## 10. 必须验证的场景

- 三个 profile 都拒绝技术通过但没有本次 SDD 验收；原生 completed/旧报告/人工 gate/例外不可替代。
- light 真正的最简原生 SPEC + 同文档非空标准，无架构/Story/计划可满足前置；占位或只有标题拒绝。
- 保留 Provider 原生路径与版本前置；无计划不强制新建，已有绑定计划不得隐式缩减。
- 命令实际执行并验证全项结果；Skill 当前 run 提交同样严格；空/缺项/重复/未知/失败/缺证据拒绝。
- SPEC/标准/设计、需求、代码、规则或执行声明变化会 stale；不能偷改条目减少覆盖范围。
- 新执行失败/中断不复用旧成功；输入变化与并发决策同时发生时，不丢决策、不认证旧输入。
- 报告输出边界、真实路径/链接、报告变更、输入冒充报告，以及验收修复代码后必须重验。
- 技术门禁 zero tests、缺工具/覆盖率未达项目标准仍失败；新 SDD gate 不得掩盖这些失败。
- 无入口/无 Skill/无交互通道明确 blocked；无静默替代、无自动安装/重锚/Work 重建。
- Host 提醒进入模型、不额外 turn，产品 allow/状态 deny，Dashboard 不错误关闭。
- 老 active/reopened 补新契约，completed 历史不重认证，旧正式回归与 package 资源保持兼容。
