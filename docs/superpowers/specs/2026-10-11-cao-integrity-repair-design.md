# CAO 正确性与集成修复设计

日期：2026-10-11

基线提交：`8ac90f3`

状态：用户已确认方案草案与提醒模式；本文固化该方案，供书面审阅。本文不是已完成修复的声明。

## 1. 目标与范围

采用渐进加固，保留现有 CLI、JSON 状态布局和 SDD 所有权边界，解决错误完成、并发丢更新、活动任务串扰、路径保护绕过以及主机事件失真。

本轮不改用 SQLite，不引入事实图谱、通用任务调度器、后台文件监视器或 Shell 安全沙箱，不把 CAO 改为 SDD 框架。

### 已确认的产品策略

- 缺少有效路径评估或存在重大需求歧义时，提醒风险与下一步，但不阻断产品代码写入。
- 无活动 Work Item 时允许需求录入、读取、SDD 文档生成和 CAO 治理命令；产品代码写入给出治理提醒。
- 对已识别的 CAO 内部状态直接修改实施硬保护，需求文档目录仍允许 Agent 编写。
- `cao done` 是权威完成入口，未满足需求版本、工作流、计划、门禁和验证条件时必须拒绝。
- 不新增实施前强制阻断模式或模式切换配置。
- Host 适配器不可用时不阻断所有工具，也不虚构保护已生效；可检测的安装、调用和解析失败需报告诊断。

## 3. 全局约束

- Python >=3.10；Python 核心仅使用标准库，不新增第三方运行时依赖。
- 保留 `cao` 入口及现有命令；新增配置入口仅服务于修复所需的门禁声明。
- 保留 `.orchestrator/work/`、`sessions/`、`handoffs/` 与 `lifecycle/events.jsonl`；不迁移到第二套状态库。
- Work Item 是执行状态权威源；`index.json` 是投影；Session 与 Handoff 不复制独立执行状态。
- 新增代码文件不超过 500 行；不为满足行数限制一次性重写现有大型文件。
- UTF-8 文档；保留项目语言偏好与 Provider 原生文件所有权。
- 验证命令和 SDD 安装命令属于受信任的项目代码；CAO 不承诺隔离其副作用。
- 本轮实现和提交必须逐任务进行；不得在用户仅确认文档时开始修改业务代码。

## 4. 模块边界

现有 `scripts/cao.py` 保留 CLI 路由和编排。仅抽取与修复直接相关的职责，避免全面重构：

| 文件 | 职责 |
|---|---|
| `scripts/state_store.py`（新增） | 仓库锁、原子 JSON 写入、读改写边界、恢复基础设施 |
| `scripts/completion_policy.py`（新增） | 需求/验收版本绑定与统一完成、门禁判定 |
| `scripts/path_guard.py`（新增） | 真实路径归属、结构化写目标与 patch 目标校验 |
| `scripts/verification_runner.py`（新增） | 子进程超时、有限输出、规范化执行结果 |
| `scripts/cao.py` | CLI、Provider 关联及事务内领域更新，调用上述边界 |
| `hosts/pi/coding-orchestrator.ts` | Pi 原生事件转换、上下文及纠正消息传递 |
| `scripts/dashboard.py` | 使用统一状态语义进行投影，不另建完成判定 |

模块提取与相应修复同一任务交付，不先建立空抽象。接口签名、具体补丁与测试代码在书面设计确认后的分阶段实施计划中锁定。

## 5. 状态一致性设计

### 5.1 仓库级事务边界

所有 CAO 状态修改入口共用仓库级跨进程排他锁，覆盖重新读取、条件检查、领域修改和保存。包括 CLI、Host 事件、Dashboard 确认，以及查询触发的原生 SDD 同步。

进程内须串行化线程，并允许同一事务中的安全重入，避免底层 save 再次加锁造成死锁。锁以规范化仓库路径为键，Linux/macOS 使用标准库文件锁，Windows 使用标准库锁实现；锁文件是否存在不能单独代表所有者仍然存活。

不得仅锁最后的 `save_json`，也不得依赖 30 秒文件年龄判断一个正在工作的写入者已失效。等待有明确上限，超时返回可诊断错误。

### 5.2 原子写入与恢复

在目标同目录创建临时文件，完成 UTF-8 序列化、刷新和持久化后使用原子替换。支持的平台同步目录元数据；失败不得截断旧记录，临时文件在错误路径清理。

JSON 多文件更新不具备数据库事务原子性，因此明确以下恢复边界：

1. Work Item 先持久化，随后刷新 `index.json`；投影不一致时从 Work Item 重建。
2. 活动任务切换先将旧任务挂起，再激活目标，所有步骤均在同一锁内。
3. 中断后允许零个 active，不允许根据过期 index 偷偷激活任务；继续操作需明确选择。
4. 若历史数据已有多个 active，报告冲突及候选项，要求显式解决，不任意挑选一个。
5. Handoff 序号分配和去重在同一事务内完成。
6. 关键状态转换的待写审计事件随权威记录保存；恢复时补写 JSONL，依据事件键去重。不是两文件跨原子提交，也不扩展为通用消息执行器。

### 5.3 活动任务约束

`start`、`resume --reactivate`、`unblock`、`reopen` 统一遵守“最多一个 active”。默认不抢占其他任务。若解除 A 的阻塞时 B 已活动，可以清除 A 的阻塞，但 A 保持 suspended，返回需要显式切换的提示。

显式切换仍使用已有 `start --replace` 或先挂起再激活的流程，不添加静默抢占。普通 checkpoint、决策或原生同步不得改变活动指针，除非操作确实完成状态转换。

## 6. 需求和验收证据设计

### 6.1 版本分离

状态修订号用于防止陈旧写入；需求哈希及评估版本用于判定证据有效性。不能将每次 Session 活动增加的状态修订号当作需求变化，否则会使评审不断失效。

人工门禁记录绑定需求哈希和评估版本；工作流绑定需求哈希、Provider 与产物哈希；验证绑定需求、代码、规则及验收配置快照。

### 6.2 重新锚定

`start --replace` 若需求内容实际改变：更新需求锚点，清除当前路径评估、人工门禁、验证和原生工作流完成/执行有效性；保留标题、决策、进度、原生入口线索及不可变历史。旧记录不能继续作为完成证据。

需求不变时不因重复启动无条件清空进度。Provider 或评估范围改变时，按其关联范围使证据失效。

`reopen --reanchor` 用于显式接受新的验收标准：重建验收锚点并清除门禁和验证。若需求与 Provider 不变，不仅因验收标准变化要求重跑无关的原生工作流。所有重开均记录原因与独立操作标识。

### 6.3 固定验收标准

在 Work Item 开始/明确重新锚定时保存规范化验收配置哈希。验证时比较实际配置，不靠秒级 `configured_at > started_at` 判断先后，也不允许通过修改时间戳规避标准变更。

标准为空时可以开始任务，但不能完成；补齐标准后需明确重新锚定。一次性 `verify --script` 继续用于工程检查，不升级为完成凭证。

`done`、`next`、`gate show` 和 Dashboard 消费同一判定逻辑，过期的 `verification.status: passed` 本身不能表示当前门禁满足。

## 7. 显式验证门禁设计

配置示例：

```json
{
  "name": "unit-tests",
  "command": "./scripts/verify-unit-tests.sh",
  "required": true,
  "gates": ["tests"]
}
```

移除以命令字符串猜测实际测试行为的权威判定。命令名称、帮助输出或包含 `test` 的字符串不是测试执行证明。

- 配置中的 `gates` 作为显式能力声明，归入验收配置哈希。
- 必需测试门禁只能由绑定 `tests`、`required: true` 且成功、新鲜的配置验证项满足。
- 多个必需测试项必须全部通过；缺少绑定、失败、阻塞、异常、过期均不满足。
- 可选项仍执行并显示结果，但不能满足必需门禁。
- 旧字符串和无 gates 的脚本仍可作为通用验证项；不自动根据名称授予 tests 能力。
- 保留 `init --verify-script`，增加重复可用的 `init --test-script`，写入 required 的 tests 验证项，避免保护配置文件后没有合法配置入口。
- CAO 不解析各测试框架报告；项目脚本负责真实运行测试、覆盖率和零测试检查。帮助命令不能作为正式验收测试夹具。

验证运行在锁外。提交结果前在锁内重读当前状态、需求、配置及代码快照；若变化，结果记为过期或返回过期原因，不覆盖其他命令期间新增的决策、进度或阻塞。

## 8. 原生工作流与计划作用域

### 8.1 工作流成功条件

记录执行不是 CAO 代替 Provider 执行。非零退出码不得直接使原生工作流完成。`complete` 与 `done` 都检查执行成功，不能只检查 execution 对象存在。

保留 `--allow-unverified --reason` 的显式例外机制。若要接受失败执行，必须在完成操作中明确记录该失败的例外原因；不能因之前允许未识别入口而自动豁免后续失败。UI 与审计展示例外，而非伪装成功。

产物必须存在于当前 Provider 的真实输出目录，记录其哈希和需求绑定。需求、Provider 或产物改变后，原完成凭证不再有效。

### 8.2 计划作用域

计划查询接收当前 Work Item 的明确绑定，不能只接收 Provider 名称并扫描全仓库。

- OpenSpec：当前 change 目录及该需求显式关联的其他 change。
- Spec Kit：当前 feature 目录及显式关联的其他 feature。
- BMAD：关联的故事、epic 下条目或明确属于该需求的完整计划。共享 sprint 文件必须限制条目集合，不能检查全部项目，也不能只选第一篇故事。
- 多个故事/feature 属于同一需求时全部纳入；缩小范围必须由明确的需求/计划更新体现。
- 原生工作流本来不产生计划时允许记录“无计划”；存在计划但无法唯一关联时返回绑定指引，不静默扩大范围或假定没有计划。

CAO 校验声明范围内的完成性，不声称能从自然语言自动证明需求已被完整拆解。归档规则保持原生语义，不把无关活动计划计入。

## 9. 路径保护与提醒

基于规范化真实路径及目录成员关系判断，不使用子串或未解析的目录前缀。处理相对路径、`..`、符号链接、绝对路径及未创建文件的父目录。

结构化 write/edit 和 patch 提取所有目标，多文件写入逐项校验。只有真实落在 `.orchestrator/requirements/` 内的文档可以直接写入；其他内部状态由治理命令更新。

Shell 检查识别保护路径、重定向和复合命令，不因 `cat`、`ls`、`sed` 等前缀就认定只读。已确认直接修改保护状态的命令拒绝；不能可靠识别的动态 Shell 行为不声称已完全隔离。合法 CAO 治理调用不因其参数提到状态路径而被误判为手工修改。

产品代码写入仍是提醒模式，提示缺少评估、重大歧义或原生工作流未执行；多目标中出现一个 SDD 路径不能抹掉其他产品目标应有的提醒。

## 10. Host 与 Session 契约

Pi 使用 `ctx.sessionManager.getSessionId()`，按 `agent_end.messages` 的助手消息内容提取回复。未知会话不合并为一个虚构默认会话。

分别处理执行结束、最终可行动边界和 `session_shutdown`。agent_end 不关闭 Session；真正退出或切换时才结束原会话。纠正消息在支持继续执行的边界触发，并有幂等及单次继续约束，防止无限循环。

Claude/Codex 保留 PreToolUse 的 additionalContext。核对所支持宿主版本的 Stop 与 SessionEnd 能力：一轮助手执行停止不自动等同于宿主会话退出。只有宿主确实提供的生命周期事件才声明支持，不凭通用名称假设宿主有同一契约。

停止事件不再因自然语言出现“完成”硬拒绝。未完成时可以生成 Handoff 与下一步提醒，但不能将“尚未完成”当作关闭请求；完成状态仅由 `cao done` 更新。

错误诊断避免污染 CLI 的 JSON stdout，使用 stderr 或适配器 UI，并避免每个工具调用重复刷屏。

## 11. 审计与 Dashboard

每个 reopen/reanchor 具备独立操作标识；同一持久化操作的重试才去重。保留已有事件与幂等键，不重写历史。缺失 idempotency_key 不能通过 `None == None` 把不同事件合并。

Dashboard 仅以 Work Item 的 completed 状态显示需求完成。`native-sdd-workflow-completed` 不匹配为 done；状态阶段采用明确值而不是模糊字符串包含判断。

区分完成、验证通过、证据过期和显式例外。展示与 CLI 共享权威判定；正常刷新不会改写第三方 SDD 内容。

## 12. 兼容与迁移

1. 首次改变历史状态前保留可恢复备份；迁移操作幂等，并在迁移完成前保留原记录。
2. 新字段采用显式版本，不能因 missing 字段给旧证据补造一个“当前且合格”的绑定。
3. 旧 active/suspended 可继续读取和查看进度；缺少新完成证据时报告具体补齐步骤。
4. 旧 completed 保留 completed，不自动重开；显示旧版证据未经新版规则校验，不宣称重新认证。
5. 原 Session、Handoff 目录和已支持的存储格式不改变；不增加历史上已明确不支持格式的迁移。
6. 团队更新验收 gates 后，受影响活动任务需要明确重新锚定，不能静默改变验收标准。

## 13. 实施分解与验收

方案拆成三个连续交付子计划，后续分别生成可执行任务清单；每个任务包含失败测试、最小修复、定向测试、全量回归及独立提交。

| 顺序 | 子计划及任务 | 独立验收 |
|---|---|---|
| 0 | 将 R01—R15 转为正式回归与正常流程对照；修复环境隔离；将假测试夹具改为真实测试 | 缺陷测试在旧行为上稳定失败，正常样例有效 |
| 1 | A：事务锁、原子写入、投影恢复 | 并发 decision 全保留；中断不产生半写 JSON；投影可重建 |
| 2 | A：单 active、Handoff 并发与审计恢复 | 不产生两个 active；普通更新不抢占任务；每次重开可追踪 |
| 3 | B：需求版本、验收配置绑定和历史数据兼容 | 新需求不能复用旧证据；秒内改变标准也被检测 |
| 4 | B：显式验证项和工作流退出码 | 包装脚本可用；可选失败不能满足 tests；失败工作流不能正常关闭 |
| 5 | B：计划作用域与路径边界 | A 不受 B 阻塞；A 全部关联条目仍被检查；所有已复现绕过被拒绝 |
| 6 | C：Pi API、Session 生命周期及 Claude/Codex 输出 | 正式载荷测试通过；不同会话不碰撞；退出才结束；上下文保留 |
| 7 | C：停止语义、Dashboard、诊断与文档 | 否定表达不误阻断；UI 不提前完成；文档明确提醒模式 |
| 8 | C：快照剪枝、子进程超时/有限输出 | 忽略目录不遍历；超时明确失败并清理；大输出内存有界 |

先完成状态基础，再修复依赖其一致性的证据与集成。不得一次性改完所有子系统后才回归。正式执行默认当前会话顺序进行；只有用户明确授权后才使用子代理。

性能修复中，快照应在遍历前剪枝；读取错误不能静默作为“未变化”。验证超时应终止并回收所启动的进程组，报告 error，输出保留有限尾部。配置、代码、规则、需求新鲜度语义不得因优化而削弱。

## 14. 发布门槛
