- 业务级闭环：Work → 路径与原生契约 → 按 provider 要求规划/审批/实现 → 正确绑定的原生评审 → 项目技术验证与逐项任务验收 → 原生 Finalize → CAO done。

## 一、已确认的产品目标

用户已确认：空项目在 bootstrap 完成技术栈选择后，应继续确认项目标识与布局，生成该技术栈的最小可运行骨架，建立并试运行验证基线，然后才进入业务 Work 和 SDD 开发流程。

目标顺序如下：

1. 完成 SDD provider 选择、安装及必要的 host 重启。
2. 恢复原始用户需求，检查实际产品文件，识别项目或目标模块是否需要初始化。
3. 恢复或确认项目级技术栈及必要版本。
4. 按已选择的技术栈组合，对缺失的项目标识、命名空间/模块标识及目录布局集中确认。不存在的维度不强行询问。
5. 生成可审查的初始化计划，按已确认配置创建最小骨架。
6. 建立验证入口，执行该项目实际适用的构建/语法/类型检查、最小测试和启动或导入检查；不存在编译阶段的语言不强行要求编译。
7. 记录项目初始化结果；检查成功后允许创建业务 Work，继承项目背景并进入对应 SDD 流程。

此过程属于项目级生命周期，不依赖临时业务 Work，不得为了创建构建/包管理清单、应用或库入口、测试及验证脚本先虚构一个 Work。项目背景也不能通过 Work decision 冒充项目级事实。

初始化检查通过只证明项目骨架及验证链路可用，不能证明业务需求已完成。最终仍须满足项目技术验收、任务需求验收，以及所选原生 SDD 路径的规划、审批、评审和完成要求。

## 三、不可破坏的约束

1. 保持原有需求、Work、原生 SDD 绑定、决策、审批、验收与历史证据；不得通过重建 Work、init --force 或回滚阶段恢复流程。
2. 初始化状态与结果由 CAO 命令管理，不允许 Agent 手工篡改派生状态。
3. 不得将 src/main、src、scripts 或整个仓库设为永久写入例外。
4. 不得仅凭脚本位于 scripts/verification/，或命令包含 test、verify 字样就授权执行。
5. 不得把测试命令视作真正无副作用的只读命令；构建和测试会写报告、缓存及产物。
6. 不得用 echo、true、空测试集或跳过全部测试伪造基线成功。
7. 不得以初始化名义生成业务功能、擅自增加数据库/认证/消息队列、完成需求验收或绕过原生实现授权。
8. 不得反复要求用户确认已确认信息；仅确认缺失项、实际冲突或超出原授权的变更。用户已明确委托的常规默认值可按委托范围决定并记录来源。
9. 所有共享规则必须覆盖 BMAD、OpenSpec、SpecKit 及现有其他路径；不得把共享初始化逻辑实现为 BMAD 特例。
10. 不得把 host hook 的静态命令分类描述成操作系统沙箱；对任意脚本内部效果的限制能力必须如实说明。
11. 项目初始化核心必须与语言、框架、包管理器、构建工具无关；禁止把 Java/Maven 的字段、目录、测试运行器、报告格式或成功标准提升为全局规则。
12. 不得把“已支持多语言”实现成只有 Java 能执行、其他语言只显示 unsupported；未知技术栈也必须能通过通用显式计划完成同一生命周期。

## 四、项目识别与项目标识契约

### 4.1 识别实际产品状态

区分空产品、已有可识别产品、部分初始化及产品结构冲突。已有仓库仅包含 README、版本控制元数据、CAO/host 安装目录、SDD provider 或规划产物时，不能据此判断产品骨架已存在。

识别应支持 scope：根项目已有代码，并不代表待创建的新模块已有骨架。不能因为一个模块需要初始化就阻塞其他无关模块。继承根约束，并明确模块边界与共享文件的归属。

已有产品优先复用真实构建文件、测试入口和目录结构，不套用新模板，不主动重排源码。不完整状态必须给出待补项，禁止通过“目录非空”跳过初始化检查，也禁止无条件覆盖。

### 4.2 通用模型与技术栈组合适配

核心层统一管理 scope、来源证据、确认状态、计划、文件清单、执行、门禁和结果；生态特有语义由可组合的适配规则提供。禁止在 bootstrap 或 host 门禁里不断增加 language == java 一类分支。

技术栈分别表示 language(s)、framework、runtime/toolchain、package_manager、build_tool、test_framework、delivery_kind 及各自版本/适用性。它们不能混为一谈，也不是每个项目都需要全部维度：npm 可能负责包管理和脚本执行，实际构建由其他工具完成；Python 项目可以没有独立构建步骤；C/C++ 可以使用多种构建工具。支持未指定、已确认和确实不适用等状态，不能为了通过 ready 检查虚填工具。

优先兼容现有项目背景 schema，增量增加缺失维度和版本；不把整个背景系统作为本次重写对象。ready 所需字段由所选组合及交付类型决定，不再全局强制每种语言都有 build_tool 和 test_framework 字符串。

通用身份模型至少承载项目显示名、生态内机器标识、scope 根路径、来源与推导关系；命名空间、发布坐标、导入标识、模块路径、程序/库入口等采用适配器声明的可选字段及 schema。不得用一个 packageName 字符串同时表示所有生态中的不同身份。

以下是适配设计示例，实际规则需按选定工具和版本的官方规范校验：

| 生态/工具组合示例 | 按需确认的身份 | 推导与布局重点 |
| --- | --- | --- |
| Java/Kotlin + Maven | groupId、artifactId、package/namespace、模块位置 | 发布坐标与源码包名分开；语言源集按组合确定 |
| Java/Kotlin + Gradle | group、project/module name、package/namespace | 不强制填写 Maven artifactId；支持语言及源集差异 |
| JavaScript/TypeScript + npm/pnpm/yarn 等 | package name、可选 scope、workspace、应用类型 | npm scope 不是磁盘目录前缀；src、入口和构建输出按框架/模板确定 |
| Python + pip/uv/Poetry 等 | distribution name、import package、项目布局 | 发布名与导入名分开；flat/src layout 可选，不盲目按点分包生成全部目录 |
| Go + modules | module path、package、应用或库类型 | module path 不能直接当本地根目录；cmd/internal 等布局按所选形态决定 |
| Rust + Cargo | package name、crate 标识、bin/lib、workspace member | 包名与代码引用标识分别校验，明确入口与成员路径 |
| C#/.NET + dotnet/MSBuild | project/solution name、root namespace、target framework | namespace 不强制等于文件夹；应用/库模板决定启动和测试结构 |
| C/C++ + CMake/Meson/Make 等 | project/target name、语言标准、应用/库类型 | 不要求 packageName；include/src/tests 与目标关系由计划声明 |

这些示例不是封闭的语言白名单。Ruby、PHP、Swift、Dart、其他语言或用户自定义工具链，必须能够经通用显式计划接入。

每个适配规则应输出相同契约：匹配条件与版本、所需身份字段及校验规则、推导值及来源、布局与最小骨架清单、生成方式、适用检查能力、执行命令、输出/缓存范围以及不支持或冲突的诊断。

按语言/工具链、包管理或构建工具、框架、交付形态及布局组合解析，而不是要求为每个组合复制一套完整模板。规定明确优先级：用户已确认配置和已有仓库事实优先，用户模板/生成器明确声明的约束参与校验，适配器默认值最后填补缺失。冲突必须报告，不能偷偷切换构建工具或框架。

记录最终解析的规则 ID/版本和来源，使重启可恢复、更新可检测、结果可追溯。同一语言更换构建工具不丢失仍适用的已确认身份；同一工具服务多语言时不强制只选一种语言。多个不同技术栈模块分别解析 scope，明确共享 workspace/solution 文件的管理者。

### 4.3 确认与推导规则

- 仅询问适用于当前组合、影响产物且尚未确认的字段；用户已明确委托的默认选择不重复询问。
- 发布名、导入名、命名空间、模块路径和本地目录是不同概念，不能采用统一的“替换连字符，再把点改斜杠”算法。
- 先展示建议值及映射，再保存来源。所有影响源码导入或公开标识的归一化必须可见；用户能覆盖合法值。
- 校验目标生态的标识符、保留字、长度/字符约束，以及当前文件系统的大小写碰撞、保留文件名、目录穿越和 scope 边界。
- 例如 Java artifactId=order-service 可提出合法包名建议；Python 发布名 order-service 的导入名需另行确定；npm 包 @acme/order-service 的磁盘根目录不应机械展开成 @acme/order-service；Go 模块标识不能机械创建同名远程域目录。
- 当前目录是默认候选，不因为发布名或模块名变化就自动多套目录。
- 一次呈现必要字段与“标识 → 入口/源目录/测试目录”的预览，集中确认；保存实际 host 可观察的用户证据。
- 不存在包/命名空间概念的项目跳过相应字段；库项目不能强行生成服务启动类。
- 重启或“继续”时恢复已确认值、已解析适配组合和布局，不重新选择技术栈、命名或创建需求。

### 4.4 内置规则与未知技术栈的通用路径

内置规则用于提高常用生态的准确性与自动化程度，不是执行初始化的准入白名单。不得要求 CAO 内置每种语言的生成器，或在核心层嵌入所有模板。

没有匹配内置规则时，Agent 根据用户已确认技术栈、可信模板/官方资料或现有仓库模式，形成符合统一 schema 的显式初始化计划：列明身份规则依据、推导结果、确切文件内容/来源、生成方式及真实检查入口。CAO 校验计划结构、路径边界、来源/授权及执行结果，仍走相同 plan/apply/check/ready 流程。

显式计划不代表 CAO 能自行证明任意语言语义正确。相应语言的实际构建、导入、启动和测试证据必须补齐；规则不确定时仅澄清缺失事实。只有工具、资料、授权或关键配置确实缺失时才 blocked，不能因语言未列入注册表直接终止流程。

不要为支持这个回退路径增加一个永久执行任意代码的插件白名单。自定义规则/生成器仍受相同计划、内容绑定、执行目的和文件冲突规则约束。

## 五、项目初始化状态与下一步决策

### 5.1 建立独立且简洁的状态模型

建议使用少量阶段表达 `context_required → identity_required → scaffold_pending → baseline_pending → check_pending → ready`；阻塞、失败、stale 和可恢复执行状态作为结果属性或等价建模。可以结合现有结构简化名称，但必须清晰区分：

- 已确认技术栈不等于项目身份完整。
- 已登记骨架计划不等于文件已生成。
- 已配置检查不等于检查执行成功。
- 初始化成功不等于业务验收成功。

状态至少关联：schema 版本、scope、项目背景 revision/fingerprint、初始化计划与文件清单、生成器/模板来源、验证声明与脚本内容绑定、当前执行与历史摘要、最后失败原因、唯一下一步动作。

优先复用现有事务、锁、运行记录、快照、脚本执行和来源证据模块，不新建一套平行的基础设施。若现有运行记录只接受 Work ID，应增加明确的项目级所有者类型，不能伪造 Work ID，也不能把不同 scope 的执行混入一个无归属记录。

### 5.2 统一推进判断

bootstrap、next、resume、context 展示、host pre-tool 及相关 CLI 必须调用同一份项目准备状态判断；不要各写一套阶段优先级。

provider restart 前提仍优先执行。无 Work 的新项目未 ready 时，引导完成项目初始化，并阻止业务 Work 提前创建；需求原文和 intake 文档应持续可保存，不能重新制造“要求 Work 才能写需求”的死锁。

有 active Work 的历史项目进入兼容恢复分支：绑定项目级准备工作并在安全节点修复，保留 Work 的业务阶段与进度。已有产品不能被强制重走空项目初始化或重新生成启动类。

### 5.3 中断与并发

阶段更新使用事务及 revision 校验。生成和检查支持恢复、幂等重试；同一 scope 不允许两个相互冲突的初始化执行同时写入。长时间子进程执行不能持有全仓库状态锁，结束后重新校验执行所绑定的配置与输入。

运行中用户或外部进程修改相关配置/脚本/骨架时，旧结果必须 stale，不能覆盖新状态或标记 ready。普通后续业务源码变化不应让已完成初始化倒退；由正常技术验证快照负责发现业务变更。初始化所依赖的身份、工具链和基线发生实质变化时才重新检查受影响部分。

## 六、最小骨架生成与文件授权

### 6.1 可审查计划

初始化计划声明确切 scope、文件清单、用途、内容来源/预期指纹、允许的验证命令及生成输出。已确认初始化配置足以授权范围内的常规生成，不额外创造重复审批步骤。

优先复用用户指定模板、可信已有模板或官方生成器；需要联网时记录来源及适用版本。离线不可用时明确 blocked，不能悄悄更换技术栈。

本次必须交付可实际工作的多语言通用流程、组合适配协议和未知栈显式计划路径。常见技术栈使用小型可组合规则与可信生成方式即可，不建设庞大的模板平台。Java/Maven 只占多语言验收的一部分，不能作为唯一完整实现。

### 6.2 按交付形态生成最小内容

对应用、服务、CLI、库、前端应用或多模块项目分别确定最小骨架。按实际适配结果生成包管理/构建清单、必要入口与资源、真实最小测试及验证入口；不是所有项目都需要独立 shell 包装脚本、启动类、HTTP 服务或相同目录结构。

初始化验收由能力声明决定：compiled build、syntax/type check、import/load、startup/smoke、test 等按需组合。编译型项目应证明构建可用；解释型库可验证导入及测试；服务可做启动与退出检查；前端可做构建及合适的最小组件/行为检查。检查选择必须对应项目实际交付，不用不适用的验证步骤强行卡住流程。

所有声明为必需的测试必须真实执行并验证非空；不能以 import 成功冒充单测。确实没有运行代码的特殊产物，需按显式确认的产物类型声明相应检查，不可把“无测试”伪装成测试通过。

Spring Boot/Maven 仅作为示例：pom.xml、最小应用类、必要资源、真实上下文测试及兼容的测试执行配置。Python、TypeScript、Go 等使用各自适用的清单、入口和测试，不能复用 Java 的目录/类名规则。

不要默认生成登录、用户表、业务接口、复杂分层或全套中间件配置。骨架形态和交付约束写入项目背景，使后续 SDD 能继承；SDD 需要调整结构时走正常可追溯变更流程。

### 6.3 写入边界

为无 Work 的项目初始化增加受控写入能力，绑定当前 scope、有效计划、已确认配置及允许文件。允许当前计划中应用/库入口、资源及测试的确切路径，不允许整个业务目录通配。

支持 host write/edit/apply_patch 及实际采用的生成入口；所有入口共享授权判断。不能只保护一种工具名称，却让另一种工具绕过。

状态文件仍只能通过 CAO 命令修改。生成器尽可能先写临时目录，校验路径、符号链接、文件清单及冲突后再应用。任意外部生成器不能因名称匹配就直接在产品目录无限写入。

已存在且内容一致的文件可以复用；不同内容必须保留并报告冲突。重试不删除用户文件。若确需覆盖，给出具体差异并依据用户授权处理，保留恢复依据。失败回滚只处理本次生成且尚未被外部修改的文件。

## 七、验证执行入口与门禁统一修复

### 7.1 独立检查目的

至少区分三种执行目的：

| 执行目的 | 是否要求业务 Work | 是否要求业务评审完成 | 是否可用作最终业务验收 |
| --- | --- | --- | --- |
| 项目初始化检查 | 否 | 否 | 否 |
| active Work 内基线准备/诊断检查 | 是 | 不要求尚未到达的评审阶段 | 否 |
| 正式技术验证及任务验收 | 沿用现有要求 | 沿用所选路径的要求 | 按现有双重验收契约 |

初始化检查与 Work 准备检查可以复用底层 runner，但执行目的、归属和证据必须分开。不能为了支持初始化而删掉 `cao verify` 的现有最终验证前置条件，也不能让 `cao verify --script` 成为绕过入口。

### 7.2 候选 CLI 契约

结合已有 CLI 设计落地以下能力，命名可合理调整，但交付时必须提供真实可执行的 help 与调用示例：

- 查看/设置项目身份与布局：扩展现有 project context 能力，或提供明确的 identity 子命令；参数/schema 不能只支持 Maven 坐标。
- 查看适配组合与字段要求：展示匹配依据、规则版本、缺失字段及通用显式计划接入方式；避免新增语言就必须改核心 CLI parser。
- 项目初始化 status/plan/apply：查看准备状态、建立受控计划、生成或应用骨架。
- 项目初始化 check：执行已登记的初始化检查。
- active Work 基线 check/probe：在实现授权前允许对已登记验证入口做准备性试跑。

例如 `cao project setup status|plan|apply|check` 和 `cao verification check --work <id>` 都是候选接口，不是已存在命令。必须检查命名冲突、参数、schema、错误码、compact JSON 和帮助文本，并复用仓库现有风格。

保留 `verification configure --plan-only` 作为兼容的声明能力，但它不能单独使新空项目进入 ready。实际基线有唯一配置源，项目 setup 不再复制一套可相互漂移的脚本配置。

### 7.3 命令分类一致性

将纯读取、产品写入、受控生成、构建/测试检查、依赖准备等行为分清。移除“mvn test 等价于普通只读”的宽泛判断，接入与包装脚本相同的阶段授权原则。

推荐由 CAO 专用检查入口执行登记命令；外部直接调用若不能证明符合当前 scope 和检查授权，应给出该入口的确定性恢复指令。不要按脚本名字、目录或 test 子串放行。

直接测试命令、包装脚本、不同解释器调用形式，以及脚本内再调用测试，必须在同一检查入口下正常工作。不得出现功能相同、仅包装形式不同就一方允许一方拒绝的语义差异。

授权至少绑定 scope、工作目录、声明、验证包装脚本及可识别本地依赖文件的内容、项目配置 revision 和执行目的。任意脚本内容发生变化后不能继承旧批准或旧成功结果。复用现有快照机制处理传递依赖，不宣称能静态完整分析任意 shell。

复合命令、重定向、解释器 -c、变量展开、符号链接及外部工作目录必须显式处理。无法可靠分类时给出结构化拒绝和合法恢复入口，不指导 Agent 换 shell 写法避过门禁。

### 7.4 检查执行与结果

复用现有 timeout、进程树清理、日志尾部、运行记录、并发提交保护和快照校验。配置命令应使用结构化参数或正确 shell 转义，避免将用户标识拼接成可执行 shell。

保留 PASS、FAIL、BLOCKED、ERROR 的现有退出码语义。无测试、工具缺失、依赖缺失、超时、执行中修改输入、执行失败均不得标记 ready。

“已声明脚本”与“验证标准已确认”与“脚本执行通过”分开保存。准备阶段允许失败后修复已授权的骨架/脚本并重试，不能要求“先通过检查才能修复检查入口”。

生成报告、构建输出和缓存必须由当前适配结果在执行前明确配置边界，不能只支持 Maven target/；已跟踪文件及真正源码不能因输出目录名称而自动消失。不能通过清空快照或把整个源码目录排除来解决 stale。

依赖下载遵循已确认构建方式及现有安装授权，限制在适当的项目/构建环境；不能默认授权全局安装、系统配置修改或未知远程脚本。已授权的正常构建依赖解析不反复询问。

检查 runner 执行的子进程通常不会产生新的 host pre-tool 事件：应在受控入口正确记录命令和结果，不假设 host 可以逐条审查脚本内部调用。若没有真实进程隔离，文件快照只能检测部分越界，不能据此宣称任意脚本被安全沙箱化。

## 八、审批、最终验收与历史兼容

### 8.1 避免初始化审批循环

项目身份确认和验证标准确认属于项目级事实。用户已明确确认的标准，应能以有效项目证据绑定到后续 Work；不要在 bootstrap、Work start、BMAD Build 中反复询问完全相同的问题。

现有原生 provider 若有独立的强制审批契约，必须明确与项目确认的关系：能复用的证据通过显式兼容规则复用，不能复用时仅询问该阶段真正新增的审批内容。禁止把 Agent reason 当作用户批准，也禁止假造“继承批准”。

对标准、脚本或验收范围的实质更改，沿用有效的 review/reanchor 规则；不能静默更换标准并让旧结果保持有效。

### 8.2 已有项目及 active Work

- 已有可识别产品走复用与检查路径；不强制补齐全部新建项目字段，不重建骨架。
- 旧配置只有 plan-only：在安全恢复节点完善实际骨架与基线，不视为成功证据。
- 已有 actual scripts：复用并校验绑定，不重复生成包装脚本。
- active Work 的基线准备检查必须可用，解决本次发现的脚本试运行问题；不要求先完成尚未到达的 SDD 评审。
- 已完成 Work 的历史状态、旧记录不批量重写或重新认证。
- 新增 schema 与背景指纹时提供明确兼容/迁移策略。缺少可选身份字段不能让所有旧项目突然变成 invalid；实质变更导致的旧证据失效要明确说明。
- 初始化完成后第一次 Work start 继承项目背景与验证声明，不把项目检查结果灌入 Work 的最终 verification/acceptance 字段。


## 九、原生路由契约、审批与实现交接

### 9.1 在执行前解析完整原生契约

路由 check/propose 不只接受 primary artifact 和局部 rule 引用。对当前 provider、版本和路径，解析实际适用的规划、实现、评审和完成规则，并记录来源、版本、内容指纹与适用条件。不能要求执行到评审才发现此前认可的路由缺少评审契约。

BMAD 模板源和渲染快照需要明确区分。模板可含动态变量或不含最终审查层；运行时以当前有效且完整的渲染结果为准。避免仅从某条规划规则文件的相邻路径猜测所有后续步骤。其他 provider 采用自己的原生契约，不要求生成 `_bmad/render` 或 BMAD 评审层。

当前原生规则若允许 freeform direct-build，CAO comprehensive 不自动等同于必须生成独立 PRD、架构和 sprint 文件。CAO 风险档位与 provider 原生路线分别表达；允许的省略需有当前规则和替代产物证据。不能把自由路线变成豁免原生规划、评审或验收的万能开关。

### 9.2 证据修复与语义变更分开

提供复用现有机制的受审计修复路径，比较 requirement、frozen intent、路线语义、义务集合、原生规则内容和版本，而不是只比较 route ID 或文件路径。

- 只调整等价来源定位、补充定位元数据且实际契约不变：验证内容等价后保留/迁移仍适用的审批、handoff 和评审关联，记录旧新来源及理由，不重新问同一 SPEC。
- 模板源换为渲染结果：不能仅因文字近似就认定等价；实际展开改变层或义务时按语义变更处理。
- 冻结意图、需求、关键约束或义务发生实质变化：按 provider 正常 loopback、重新审批及相应重评处理。
- 无法证明等价：给出缺失证据及针对性恢复，不伪造继承批准。

### 9.3 审批请求先绑定，用户只回答一次

按 provider 契约，在展示最终 SPEC 和发出审批问题之前建立当前请求，绑定 Work、主会话、当前意图/契约及问题调用。结构化问答结果必须与该请求关联。不要先询问、修改 ready 状态，再发现没有 CAO request 而重复询问。

项目身份确认、基线接受、业务 SPEC 审批是不同对象；同一对象的同一有效版本不重复确认。初始化标准可合法继承，不代表业务 SPEC 自动获批。代理说明、reanchor reason、技术选择或泛化“继续”不能代替原生强制审批。

批准并停止必须保留已批准内容并暂停；恢复词与当前 provider 契约一致。重启、切换会话或修复等价证据不重新 intake、不倒退业务阶段。

### 9.4 实现 handoff 必须可观察和恢复

实际派发实现任务时记录 task/run ID、parent/native child session ID、角色、当前 Work、SPEC 意图、实现契约、模型及工具能力。完成时关联真实任务结果、变更集合和验证输出，而不是以 renderer 执行或手填 exit-code 证明实现工作流发生。

路由证据修复、host 重启、会话压缩或上下文恢复后，读取已持久化真实关联；优先迁移仍有效证据。缺少历史证据时明确 pending/blocked。保留已有合规例外能力时，需按其范围和授权执行并在最终报告标出；不能将 `--allow-unverified` 作为正常路径、自动兜底或后续全部义务的豁免。

## 十、独立原生评审身份、冻结输入与结果来源

### 10.1 任务身份与会话身份必须一一对应

至少将以下关系纳入现有状态/运行记录：

`Work + review round + layer + review run + input digest ↔ launched task/run ↔ actual child/native session ↔ returned original report`

不能按 sessions list 的顺序、启动时间、返回顺序、模型相同或“都是当前 Work 的子会话”推断角色。

本次第一轮复现必须覆盖：

| 实际 native session 后缀 | 实际任务 | 当时错误绑定 |
| --- | --- | --- |
| dafdcc3da427 | edge-case-hunter | blind-hunter |
| 59fcbf7b37a1 | verification-gap | edge-case-hunter |
| b97d30711bcd | blind-hunter | verification-gap |

第二轮同样存在循环错位；不允许只修第一轮特定排序。并行任务列表任意重排、延迟启动或反序返回均须正确。

宿主若不能提供足够关联信息，保持 pending，提示具体缺口或使用既有独立会话/人工返回契约。不能引导代理猜 child ID。read-only 审查员不承担 shell attach；由协调器使用真实运行时关联完成 attach，再通知审查员开始审查。

### 10.2 attach 与报告接收都校验来源

attach 验证角色、run、任务/会话关联、父会话和输入；reject 错层、旧轮次、重复占用或不匹配报告。报告提交/分类继续核对原始输出来自已绑定 reviewer，不是有一个 attach 记录就允许接入任意 Markdown。

协调器可将外部只读输出转存到项目拥有的路径，但应保留原文与内容哈希、来源 task/session、输出路径和时间。后续 triage 可以新增判断，不能冒充原审查员改写发现。CAO 负责证据可追溯，不宣称这些记录能密码学证明模型真实阅读全部代码。

### 10.3 批量 prepare 与逐层 begin 共享实现

二者共享原生契约解析、模型/能力判断、输入构造及前置校验，批量命令只承担协调和原子准备。相同输入不能一处报缺少指令、另一处可成功且无可解释差异。

批量失败说明具体缺失/冲突的文件、字段、实际解析结果及合法下一步。修复输入后允许重试；retry_count/pause_retry 不能覆盖已改变的事实或形成永久阻塞。准备失败不得留下半套活动工单。并发创建和重试不能覆盖已存在的有效轮次。

模型默认值来自当前宿主观测，并展示来源；不从旧 worker、环境变量缺省或模型字符串猜测当前审查模型。不引入与原生独立性无关的“必须换模型”要求。

### 10.4 完整冻结输入与轮次控制

准备完整变更清单：新增、修改、删除、重命名、二进制/非代码资源、构建清单、配置、测试和必要目录占位。NO_VCS 项目用明确的基准和文件清单构造快照，不能只 find Java/YAML。

blind-hunter 是否仅获得 diff、其他层是否读取 SPEC，遵循原生各层指令，不能为了提供完整输入而破坏其独立性边界。每层只得到其契约允许的上下文，但冻结范围应一致且可追溯。

按原生要求 begin 所有层、收集所有输出、分类后再修补；只为真实 loopback 或输入变化启动必要的新轮次。UI 显示“3 个层、2 轮共 6 个审查任务”，不把它们混称为三个已正确绑定的结果。

## 十一、逐项任务验收与技术验证分离

### 11.1 明确三类结果

- 项目初始化检查：骨架、工具链与验证链路可用。
- Work 技术验证：当前实现通过适用的构建、测试、安全等项目质量要求。
- 任务验收：当前需求及原生设计约束逐项满足，且证据新鲜、范围完整。

不能把其中一种结果直接复制成另一种结果。标准/综合路径保留现有独立最终验收；light 及其他 provider 遵循其既有适用性，不制造不需要的流程记录。

### 11.2 验收目录与来源覆盖

区分源条目目录、功能验收标准、设计约束、实现任务和文档元数据。原需求 6 条、SPEC 9 条 AC 与提取的 55 个源条目不是相同计数。展示每类数量及映射，避免报“55 项功能均通过”掩盖混合来源。

保留真正需要验证的边界、非功能约束和负向要求，不因整理数量而缩小需求。源项有稳定 ID 和真实 source 定位；任务复选框、元数据不能无条件变成独立功能标准，也不能仅靠把 ID 映射到自身就宣称语义覆盖。

### 11.3 每项必须有真实检查与结论

验收声明至少能建立：

`criterion/source → check identity or evaluation → executed run → relevant evidence → passed/failed/blocked`

优先复用仓库现有 executor template、request/report schema 和 runner，不复制第二套协议。不同类型标准可以使用测试、静态检查、产物核对或符合原生独立性契约的评估；证据说明实际检查了什么。

允许多个标准复用同一次完整测试运行，但每项必须引用与该标准有关的测试用例/断言或检查输出，说明为什么能证明该条。不能硬性要求每条重新跑一遍整个测试套件；也不能把一次命令退出 0 直接广播给所有标准。

明确禁止以下模式作为有效验收：

```python
result = run("security.sh")
items = [passed_if_exit_zero(result) for criterion in all_criteria]
```

安全脚本可作为技术证据或部分验收检查，但不能自动证明所有功能、持久化、设计及文档约束。零测试、跳过所有测试、旧报告、未映射项、检查未执行或来源错误必须 failed/blocked，不得 passed。测试集合的“非空且真实执行”证据由适配器获取，不能全局只解析 Surefire。

CAO 应对协议完整性、映射完整性、执行身份和证据新鲜度负责；无法一般性静态判定任意脚本语义时如实说明，不声称能自动识别所有伪造 executor。通过提供标准映射执行器、明确协议、诊断与回归场景减少代理走捷径，而不是按重复路径/文本一律拒绝合法共享证据。

### 11.4 配置与运行时协议可直接使用

acceptance configure 能复用已绑定的 SPEC 或当前有效声明；需要显式覆盖时清楚说明，不让用户重复猜 --spec。CLI 返回当前 provider 合法的 Work-scoped output 候选或 stdout-only 方式、准确 schema 和可填模板，不用抽象 `<provider>` 目录提示迫使代理试错。

命令模式 stdout 只输出协议 JSON，过程日志走 stderr/已登记日志；skill 模式遵循其独立协议。返回 request/report 格式错误时展示具体字段、真实错误和修复方式。需要写报告时按真实注册输出管理，不能声明文件输出却只打印 stdout。

resolve 同样提供当前 run、层、可解决 finding IDs 与精确草稿，空发现能合法结束；拒绝旧轮次和不匹配 IDs。不要要求代理从旧轮次复制 JSON 猜格式。

## 十二、证据失效范围、reanchor 与流程恢复

### 12.1 建立最小充分的依赖关系

复用现有快照/代际机制，明确 requirement、意图、原生规则、产品变更、测试、检查声明、验收映射和报告各自影响的证据。不要为了本次修复建立庞大的独立证据图平台。

| 变化 | 默认需要重新判断的结果 | 必须避免 |
| --- | --- | --- |
| 业务代码/接口/运行资源改变 | 相关原生评审、技术验证及任务验收 | 保留全部旧 pass |
| 功能测试改变 | 技术验证、对应验收；按层契约判断 review | 一律不重评或一律全重评 |
| 验收执行器/映射改变 | 执行器本身检查、任务验收及受影响技术证据 | 无解释地重跑所有产品审查 |
| 报告/运行日志生成 | 当前执行结果和输出归属 | 报告写完立即污染自身输入 |
| 等价路由来源修复 | 来源绑定核对和可审计迁移 | 只因新 ID 使批准/handoff 全失效 |
| 意图/需求/原生义务实质改变 | 按 provider loopback 刷新对应批准/实现/评审/验收 | 把语义变更当路径修复 |
| Git commit、会话重启 | 重新核对输入一致性 | commit 或重启本身就要求重做所有门禁 |

依赖判断应覆盖验证工具可能改变产品语义的实际情形；不能把 scripts/verification 整目录从所有快照永久排除。失效时输出 changed inputs、受影响层、仍有效结果和确定下一步。不能仅报 NATIVE_REVIEW_STALE。

### 12.2 reanchor 不应隐式重置完整工作流

reanchor 仅接受当前经过审查的输入基线；不得补造用户批准、通过未执行检查、清除未完成义务或把已完成实现重置成要重新 select/execute 的工作流。业务阶段和历史保留，确需重新执行的部分由依赖变化明确决定。

用户说“继续”时恢复当前主任务、暂停/批准状态、已有证据和合法下一步；不重走 intake、不创建新需求、不用新 Work 绕过阻塞。repair 元数据与重新执行功能工作分开。

### 12.3 不重复启动 CAO 功能评审

CAO conformance 检查 provider 声明的产物、过程、审批、范围与证据。已具有效原生功能审查时复用对应门禁。独立 security review 是否另有未满足义务，应展示其契约和差额；不能只用人工说明假装完成，也不能无条件再启动同一代码审查。

可选项目知识收集继续复用已有能力，不作为额外强制门禁，不扩大本次范围。

## 十三、统一命令授权与可恢复诊断

### 13.1 控制命令在阻塞时仍然可达

精确识别只读查询、协议/help、工单准备/绑定/分类/解决、合法恢复与产品写入。当前门禁不能拦截解决自身所必需的 CAO 控制命令，也不能把所有 cao 子命令无条件放行。

对同一请求的单条命令、真实采用的循环/复合 shell 形式保持一致的授权语义。无法可靠解析时返回单条可执行的合法控制命令或结构化入口，不指导换壳绕过。处理重定向目标和附加命令；允许读状态不代表允许覆盖产品或状态文件。

read-only reviewer 由协调器承担需要 shell 的控制动作。解析状态若使用 shell pipeline + Python heredoc，要避免 stdin 被脚本正文占用；示例采用可实际运行的 `python -c` 或文件方式。不能靠 `head/tail/grep` 剪掉核心错误后只看到局部成功。

### 13.2 当前错误与全局后续阻塞分开返回

保持既有 JSON 兼容，增量提供或统一：命令结果、error/reason、field、expected/actual、相关 owner/work/run/layer、输入变化、repair action、retry 条件与总生命周期 blockers。

- 失败不能仅给 ok:false/error:null；明确是哪一步失败。
- acceptance 输出无效时先报告协议错误，不能 next 只叫满足 security_review。
- 返回真实可用的命令，避免 verification status、work show 等不存在的建议。
- retry/pause 依据当前输入和失败类型，不把过期计数当作永久拒绝。
- 单条和批量命令复用诊断，错误不改变已有效状态；状态查询不要求提前完成其正在展示的审批。

诊断保持紧凑，用户概要与模型完整结构化信息分开呈现，复用已有 host 展示适配；不把整份运行时状态反复灌入用户窗口。

## 十四、原生完成、CAO 关闭与最终声明

建立 provider-specific completion contract：当前范围的任务完成、适用评审已分类/解决、技术验证与任务验收有效、原生 Finalize/Commit/Archive 或终结状态满足之后，CAO 才允许关闭。

BMAD 当前有效 SPEC 仍 in-review 时，必须给出合法的原生完成动作或明确该版本为何可处于该状态；不能只因复选框全打勾就跳过最终状态。不要让 CAO 静默改 YAML 为 done 代替实际原生完成步骤。

Git 仓库与 NO_VCS 情形分别遵守原生规则：不强制 NO_VCS 虚构提交，也不把所有情况的 commit 都默认不适用。OpenSpec/SpecKit 检查自己的 archive/finalize 契约，不套 BMAD 状态名。

CAO 与 provider 更新采用可恢复顺序：完成前校验当前输入；需要修改原生产物时通过正常授权动作，并防止终结元数据造成无限 stale。中断后识别已完成步骤并幂等继续，不出现 CAO completed 但原生终结尚待执行且所有写入又被无 Work 门禁阻止。

最终输出区分实际测试数量、原生评审层/轮次、验收条目类别、未验证例外和原生完成状态。不得把 allow-unverified 隐去，不得把批量退出码映射说成逐项独立验收。历史已完成 Work 不批量改写；发现历史不足提供诊断或用户要求下的有界恢复，不伪造历史批准。

至少检查以下模块及其实际依赖，按最新仓库结构调整，不盲目堆入大型入口文件：

- `scripts/cao_bootstrap.py`、bootstrap/next/context/指导文本相关模块。

- 当前实际的 `native_obligations.py`、`review_dispatch.py`、review diagnostics、native sync、路由/审批/实现 handoff、sessions 与 child hooks 模块。

## 十六、项目初始化必须覆盖的测试与验收矩阵

先写能复现真实缺陷的回归测试，再实现修复。测试既覆盖允许路径，也覆盖拒绝及恢复路径；不只断言固定提示词字符串。

| A21 | BMAD/OpenSpec/SpecKit 及 light/standard 等路径 | 共享初始化规则一致，原生门禁不被削弱 |

| A23 | baseline 确认、继承、变更及 reanchor | 不重复询问同一事实，不伪造批准、不静默换标准 |
| A24 | 打包发布后在新项目使用 | 模板、模块、引用与命令齐全，根入口可运行 |
| A25 | 同语言切换构建工具，如 Maven/Gradle | 共用语言规则但保留工具差异；核心门禁无需分支 |
| A26 | 同工具用于不同语言，如 JS/TS 或 Java/Kotlin | 选择正确入口/源集/检查，不错误继承语言规则 |
| A27 | Python 发布名与导入名、npm scope、Go module、Rust crate | 身份与路径分别校验，不机械套用 Java 推导 |
| A28 | 无独立编译步骤、库项目、非服务应用 | 能按适用能力准备，不要求不存在的构建器或启动类 |
| A29 | 多语言 monorepo | scope 独立，workspace/共享文件与依赖关系明确 |
| A30 | 无内置规则的技术栈 | 显式计划实际经过 apply/check/ready，不止返回 unsupported |
| A31 | 大小写归一化碰撞、保留名、规则版本变化 | 冲突明确，绑定正确失效，不静默改名或沿用旧结果 |
| A32 | 用户模板与内置布局不一致 | 遵循明确配置优先级，兼容约束可校验，冲突不覆盖 |

必须执行跨技术栈验证，不能只用 Java 测试作为多语言完成证据：

1. 契约与布局集成测试覆盖上表列出的至少八种生态/工具组合，核对各自身份字段、源目录、测试入口和输出边界。
2. 真实工程测试至少覆盖 Java、Python、TypeScript/JavaScript、Go 四类语言；Java 至少覆盖 Maven 与 Gradle 两种构建方式，用以证明语言与构建工具解耦。
3. 每条真实工程路径执行：身份确认记录 → 无业务 Work 的骨架生成 → 适用检查及非空真实测试 → 验证入口试跑 → ready → 创建首个业务 Work。
4. 至少一条真实执行路径不使用内置规则，由显式计划完成，证明未知栈接入能力实际可用。
5. 多语言 monorepo、规则版本变化及没有独立编译阶段的场景需有针对性集成测试。

上述覆盖是本次代表性验收下限，不是支持语言的封闭清单；也不等于一次修复即可宣称验证了所有语言和任意工具组合。不得以 mock 子进程退出码冒充真实工程执行。

同时执行仓库规定的 Python、host adapter、协议/文档一致性及发布测试。报告哪些是静态、单元、集成、真实工程或真实宿主会话验证，不声称未经执行的完整端到端通过。

如果环境缺某种工具链、host 或网络，明确列出未完成矩阵项、具体阻塞与剩余命令；继续完成可独立执行的工作，不把测试环境限制变成产品只支持 Java 的实现限制，不为通过测试替换用户技术栈或伪造结果。

## 十七、业务流程与证据闭环必须覆盖的验收矩阵

下表与 A01–A32 共同构成完整验收，不用新增场景替代原有多语言要求。

| 编号 | 场景 | 必须验证 |

| B02 | 第二轮、反序返回、并发启动 | 不复用第一轮映射，不按时间/返回顺序绑定 |
| B03 | 错层/旧 run/错误输入 digest/重复 session | attach 与报告接收均拒绝，已有正确记录不被覆盖 |

| B05 | read-only reviewer 无 shell、无可见 child ID | 协调器通过运行时映射 attach；缺证据时明确 pending |
| B06 | 批量 prepare 与逐层 begin 相同前提 | 成功/失败条件一致，失败无半套工单，修复后可重试 |
| B07 | 模板源缺动态层，渲染结果完整 | 执行前发现契约差异，采用有效快照，不等实现完成再报错 |

| B11 | 批准并停止后重启、“继续”与恢复实现 | 严守 provider 恢复契约，不重复 intake、不丢暂停状态 |
| B12 | 真实实现子代理 handoff 后证据修复/重启 | 可恢复真实关联，不常规使用 allow-unverified |
| B13 | 无真实 handoff 或 renderer-only 执行 | 不能宣称实现工作流已观测；例外单独展示 |
| B14 | 完整 diff 含 data/.gitkeep、删除及非代码资源 | 冻结输入完整，符合各层上下文边界 |
| B15 | 原生报告 Markdown/JSON 转存和 triage | 原文哈希、来源和层保留，协调器判断与原始发现分开 |
| B16 | 空 findings 和多个修复项 resolve | 正确模板一次可用，空结果合法，旧 IDs/run 不得串用 |
| B17 | 原需求 6 条、SPEC 9 条、55 个提取源条目 | 分类/映射透明，元数据不冒充功能验收 |
| B18 | 整个 security.sh 退出 0 后全项 passed 的旧模式 | 标准执行路径不能以批量退出码替代逐项检查；暴露缺失映射 |
| B19 | 一个真实测试运行覆盖多条标准 | 正确复用对应断言证据，不要求重复全套执行 |
| B20 | 未映射、未执行、零测试、全 skipped、旧报告 | 明确 blocked/failed，不制造 passed |
| B21 | 一个验收项失败、另一个通过 | 每项状态准确，总结果不通过；不因整体脚本 0 掩盖失败 |
| B22 | stdout 混入日志或 JSON 字段错误 | 定位协议错误；修正模板后可成功，日志单独保存 |
| B23 | 声明文件输出与 stdout-only | 合法路径可发现、归属正确、实际写入符合声明 |
| B24 | 新增验收 executor、仅映射变化 | 只失效依赖证据；说明为何某审查层需要或无需重跑 |
| B25 | 业务实现变化、测试变化、意图变化 | 分别触发正确受影响证据，不能过度保留或全量失效 |
| B26 | reanchor/普通 commit/host 重启 | 不隐式重置工作流，不清除有效批准，不产生自我 stale |
| B27 | 阻塞时查询、prepare、attach、classify、resolve | 所需控制入口可达；混入未授权产品写入仍拒绝 |
| B28 | 控制命令单条、循环、复合及重定向 | 授权语义一致或给单条确定恢复方式，不靠换壳绕过 |
| B29 | 当前协议错误同时存在 security_review blocker | 当前错误优先且具体，生命周期 blockers 单独列出 |
| B30 | 原生 SPEC in-review 时 cao done | 给出原生终结动作，未满足契约不得关闭 |
| B31 | 原生完成与 CAO done 间中断/并发修改 | 恢复幂等，输入变化使相关结果失效，无双边状态裂缝 |
| B32 | Git、NO_VCS、不同 provider Finalize/Archive | 按各自真实契约判断，不虚构提交、不套统一状态名 |
| B33 | 已有有效原生代码审查、独立安全义务 | 复用对应门禁，只补差额，不再跑一套 CAO 功能审查 |
| B34 | 历史 completed Work 与旧 schema | 只读诊断可用，不批量重写、倒退或伪造历史来源 |
| B35 | 最终汇报 | 测试数、层/轮次、验收类别、例外、未完成项与机器状态一致 |

必须补充真实流程验证：

1. 至少一条 Pi + 当前安装 BMAD dispatch 的真实宿主会话：空项目准备 → 首个业务 Work → 规划/审批 → 实现 handoff → 三层身份正确的独立原生评审 → 修补/resolve → 技术验证 → 逐项任务验收 → 原生完成 → CAO done。核对原始子会话头与任务内容，不只看模拟 attach 返回值。
2. 在该路径中验证受限基线试跑、正确一次审批、只读 reviewer 协调器 attach、一次等价证据修复及一次真实输入变更；不要求人为制造额外整轮审查来凑测试。
3. 对 OpenSpec、SpecKit 与已有其他 host/path 执行适用的共享层回归和实际可运行集成验证。未完成真实宿主测试不得表述成“所有 provider 已 E2E 通过”。
4. 复现本次“添加验收执行器 → review stale → 全轮重跑”链路，查出实际失效原因并验证修复后的受影响范围；不要只断言错误字符串消失。
5. 若有本次会话压缩包，可将去敏后的最小事件/状态片段整理为回归 fixture，勿将完整私人会话、绝对用户路径或密钥直接提交公开仓库。

## 十八、实施顺序、交付要求与完成判定

### 18.1 实施顺序

以下为同一修复任务的依赖顺序，可拆为可审查提交，但不能因先完成初始化而遗漏证据链闭环：

1. 读取最新 main、AGENTS.md、技能开发/测试约定、发布裁剪规则；建立独立修复分支并记录基线。检查已有工作，不覆盖用户未提交修改。
2. 建立 A/B 问题对照矩阵，区分已修复、可复现和待定位项；先加入最小真实回归测试。输出简短实施清单后继续执行。
3. 优先修复 P0 评审身份/报告来源和逐项验收：堵住“有会话但错绑”和“技术通过批量冒充任务通过”。新增约束兼容已有记录，不能假造历史关联。
4. 实现通用项目身份、组合规则、未知栈显式计划、项目级准备状态及受控骨架，复用事务、runner 和证据存储。
5. 打通初始化与 active Work 准备检查、试跑/接受顺序和一致门禁；保持正式 verify/acceptance 的适用前置条件。
6. 统一路由契约解析、批量/单层评审入口、审批时机、handoff 恢复及等价证据迁移。
7. 实现局部失效、reanchor、诊断/恢复入口、原生 Finalize 与 CAO close 闭环；消除元数据修复引发的无谓重复工作。
8. 同步 schema、help、运行时 references、provider/host 指引、模板、双语 README、示例及发布依赖，删除互相矛盾的旧指令。
9. 执行 A/B 回归、跨技术栈真实工程、实际宿主及发布安装验证；修复新暴露的问题，准确记录环境阻塞。
10. 自查代码规范、模块职责、复用、死代码、测试有效性和兼容风险，交付可审查修改及真实验收结果。

任务较大可以分阶段推进并留下恢复记录，但不擅自缩减为“先给建议”“只改技能文本”或“只支持 Java”。不开展无关重构，不另建通用模板平台、万能插件系统或与现有系统平行的状态/审批/证据基础设施。

### 18.2 最终交付

必须给出：

- 每项根因、修复行为和对应回归证据；已存在的修复只说明验证结果。
- 项目级与 Work 级生命周期、迁移/恢复及证据继承规则。
- 各生态身份/路径示例、适配扩展方式、未知栈显式计划及真实 CLI 调用链。
- 正确的 task/layer/session/report 映射，以及错绑被拒绝的测试结果。
- 至少一份真实逐项验收映射/报告示例，展示通过、失败、阻塞和共享测试证据；使用测试项目，不污染 CAO 产品仓库。
- 失效依赖说明、仍有效证据、重试/恢复方式和原生完成证明。
- 对其他 provider/host、既有产品、active/paused/completed Work、旧 schema 的影响和兼容结果。
- A01–A32、B01–B35 的结果表，标明自动化、静态、模拟、真实工程、真实宿主分别覆盖什么；未执行项列出阻塞和剩余命令。
- 安装包内运行时模块/模板/references 完整性，以及新项目从发布产物安装后的实际入口验证。
- 提交、推送、PR 的真实状态及未完成事项。按执行会话已有授权操作；没有相应授权时完成本地可审查修改，不擅自合并或发布 release。本任务书自身不等于部署/发布授权。

### 18.3 完成判定

只有以下条件同时满足，才可声明本次完整修复完成：

1. 真正空项目能够在无业务 Work 条件下，按已确认的任意目标技术栈，经内置组合规则或通用显式计划完成合法身份/布局、最小骨架、非空真实测试与适用基线检查；失败后可恢复。
2. 进行中 Work 能合法试跑验证入口并继承项目背景，不被要求提前完成后续阶段，不重复确认同一有效事实。
3. 原生契约在执行前可解析，审批与真实 handoff 可关联、恢复；等价修复不无谓失效，实质变化不错误继承。
4. 各独立评审的任务、会话、层、轮次、输入及原始报告来源对应准确，乱序和并发不能错绑。
5. 项目技术验证与任务验收明确分离，标准有逐项有效证据；一次脚本成功不能无映射批量制造所有 passed。
6. 证据按真实依赖失效，查询与恢复入口稳定可达，诊断明确当前原因；不靠无限重试、重复整轮评审或常规 allow-unverified 推进。
7. 当前 provider 原生终结条件与 CAO done 同步，历史状态兼容，最终汇报与实际证据一致。
8. 所需测试与发布验证完成；有环境阻塞时如实列为未完成，不能将“代码已改”“提示词已更新”“命令放行”或“cao done 返回过成功”单独视为完整验收。
